# v0.2 Phase 1: App統一とCLI境界の整理

この変更はv0.2へ向けた開発段階です。Native／VPS／Container／Workersで同じapplication codeを動かす設計を維持します。CLIのversion表示と生成projectの依存pinは、公開済みstableのv0.1.5を維持します。v0.2 release tagは作成しません。

## 削除したHTTP API

HTTPは`App → Context → endpoint/middleware → runtime`に統一しました。後方互換shim／deprecated aliasは提供しません。

| 削除 | 移行先 |
|---|---|
| `am.Router(State)`／`am.Route` | `am.App(State)`の`get`／`post`等、または現行compile-time route登録 |
| `am.Ctx(State)`／`am.legacy` | `am.Context(State)` |
| `am.middleware`の旧chain／Next／logger／recover | `am.Middleware(State)`、`am.Next(State)`、`am.mw`、Appのerror handler |
| `am.Server(State)`／`am.http.Server`／`am.runNative` | `app.serve(options)`／`app.requestShutdown()` |
| `am.runtime.native`の旧Server wrapper | 現行`src/serve.zig`のNative transport |

`src/legacy_ctx.zig`、`router.zig`、`middleware.zig`、`http/server.zig`、`runtime/native.zig`を削除しました。依存調査で現行App／serveがこれらを使っていないことを確認しています。旧Router専用testと旧APIのhistorical redesign documentも削除しました。

旧middlewareのbefore／after順序testはApp testへ移しました。旧ServerのGET、chunked streaming、slow-header deadline testはAppの実transportへ移し、malformed framing testと同じ経路で検証します。削除したpublic宣言が再出現しないこともtestします。

`am.Routes`／`static_router`／`static_middleware`／typed endpoint bindingは現行Appに登録する仕組みであり、維持します。Request／Response／Method／StatusなどのHTTP primitiveも維持します。

旧handlerの`ctx.app`は`c.state()`、`ctx.json(status, value)`は`c.json(value, status)`へ変更します。routeをAppへ登録し、Nativeは`app.serve()`で起動します。

未使用の`ServeOptions.read_timeout_ms`互換fieldも削除しました。`header_read_timeout_ms`／`body_read_timeout_ms`を利用してください。`write_timeout_ms`は現在未実装のreserved設定であることを明記しました。出力側のdeadline実装は残った課題です。

## CLI分割

| Module | 責務 |
|---|---|
| `main.zig`／`help.zig` | 引数、dispatch、help、unknown command、終了動作 |
| `command/init.zig`、`build.zig`、`dev.zig`、`deploy.zig` | 各commandの引数と処理の組み立て |
| `command/migrate.zig`、`update.zig`、`sync.zig`、`db.zig` | migration、project update、managed sync、D1 SQL操作 |
| `command/inspect.zig`、`generate.zig`、`api.zig` | project診断／route表示／runner、resource生成、schema diff |
| `project/manifest.zig`／`scaffold.zig`／`templates.zig` | package manifest、scaffold生成、変更していないtemplate本体 |
| `project/managed_files.zig`／`worker_glue.zig` | hash管理、変更保護、backup、capability別Workers glue |
| `cloudflare/config.zig` | provider configuration parsing／rendering |
| `process.zig`／`native.zig` | subprocess transport、POSIX filesystem ABI |

mainは約140行のentry pointになりました。コマンド、引数、help、exit code、生成物を維持します。devのprocess group、signal、watcher処理も同じ実装を移しています。

分割前後のCLI binaryで、help／version／unknown-command出力とexit code、Native／Workers／Containers／bothとcapability有無の8種類のscaffoldを比較し一致を確認しました。既存CLI unit testは各moduleへ移し、mainのtest aggregateから引き続き実行します。

update／syncは既存のhash検証、dry-run、変更拒否、`--force`時backup、build失敗時manifest復元を維持します。旧Workers templateのhashを識別する処理と`sync-glue` commandは、安全なproject更新に必要なCLI動作として残します。削除対象の旧HTTP APIとは別の機能です。

## Cloudflare operation layer

構造は`Akamata CLI → cloudflare/operations.zig → wrangler.zig → process`です。

`Operations`はdeploy、D1 create／list／execute／provisionを提供します。実行場所は`Location.local`／`.remote`、SQL実行の引数は`ExecuteOptions`で表現します。`npx wrangler`のargvと出力parseはCloudflare moduleに集約しました。command／projectは外部CLIのargvを組み立てません。runner注入によりcredentialsなしでcontract testができます。

Wranglerが唯一のdefault providerです。Phase 2ではこの境界にprovider選択を追加し、cf capabilityの不足は明示的なunsupportedか、説明可能なfallbackで扱います。現在のD1 provisioningはplaceholderのときだけcreateし、already-exists時はlistからnameでUUIDを解決します。失敗時にconfigを書き換えず、build失敗後にdeployしない契約を維持します。

現在の`deploy --containers`はLinux binaryとlocal Docker imageのbuildです。Cloudflare Containersのresource作成／image push経路は現行CLIに存在しないため追加していません。Zig／Dockerはproject build操作として維持します。

## C binding方式の比較と選択

| 方式 | SQLite | OpenSSL | 判断 |
|---|---|---|---|
| `std.Build.addTranslateC` | targetごとにvendored header変換 | pkg-config経由でsystem header変換 | 0.17では動くがdeprecated。削除 |
| 公式external translate-c | vendored headerとtargetに追従 | system version／include／link設定に追従 | 固定コミットで採用 |
| generated bindingをrepositoryへ含める | CIで再生成と差分確認が必要。target依存型を考慮 | OS／OpenSSL version／macro差で複数binding管理が必要 | portable targetを狭めるため不採用 |

公式[translate-cのZig 0.17ブランチ](https://codeberg.org/ziglang/translate-c/src/branch/zig-0.17.x)のcommit `02ff0c523fb92a38939b04d0145c4a9602a74d56`、package version 2.0.0、hash `translate_c-2.0.0-Q_BUWltOBwBYABF84EUL208pIFeUIwbBs29FmVBaafN5`へ固定しました。transitive Aro依存もpackage manifestで固定されています。masterの追従は行いません。

`Translator.init`でmoduleを生成し、SQLiteを`sqlite3`、OpenSSLを`openssl`としてimportします。OpenSSLは`link_system_libs`で`ssl`／`crypto`のheader探索を含めます。Nativeだけ`b.lazyImport`／`b.lazyDependency`を呼び、Workers-only buildではtranslatorを取得／実行しません。初回Native buildにはpackage取得とhost translatorのcompileが増えます。offline利用時はZig package cacheを事前に準備してください。

Zig更新時は対応branchのcommit／hashを固定し直し、Native SQLite test、OpenSSL署名test、Linux musl cross build、Workers fresh-cache build、generated projectを再検証します。SQLite destructor sentinelのC shimはABIのために維持します。

HTTP status／WebSocket opcodeのwire整数、metrics／traceの連続enum indexを個別に確認し、deprecated `@intFromEnum`／`@enumFromInt`を`@backingInt`／`@fromBackingInt`へ整理しました。値／checked-conversion semanticsは変えていません。[Zig公式builtin説明](https://ziglang.org/documentation/master/#backingInt)を参照してください。historical benchmarkの0.16表記は測定条件なので維持し、現行architectureの旧Server／C import／TLS説明を更新しました。

## 検証

- `zig build test cli integration tasks-test`とReleaseSafeの同一suite
- `zig build test -Dopenssl=true -Doptimize=ReleaseSafe`。公開test用RSA keyで署名byteがOpenSSL参照値と一致し、不正PEMを拒否
- `zig build cli-operations-test`。D1 create／already-exists／failure、config保護、deploy順序、db mode／config、build／dev restart・shutdown／Dockerのmock smoke
- `zig build scaffold-local-test project-update-test workers-capability-sync-test`。生成Native／Workers、migration二重適用防止、managed-file保護、capability保存
- `zig build compile-fail-test workers-realtime-test workers-wasm-dispatch-test`。compile-fail 13件、JavaScript contract 6件
- Native examplesとWorkers examples、Linux musl cross build、Workers ReleaseSafe fresh cache、package archive確認

Cloudflareのlive deploy／resource作成は実施しません。外部CLI契約はmock、Workersはcompileとhost contractで検証します。CIにCLI操作smokeとOpenSSL testを追加しました。

Native examples（chat／guestbook／bench／tasks／device_messaging）と、Workers entryを持つchat／guestbook／device_messagingを検証します。tasksは既存設計どおりNative専用です。tasksをWorkers向けにbuildするとNative std.Io依存で失敗するため、portable jobs／SSE設計と合わせた将来の課題として残します。example buildのWorkers rootは既存設定でReleaseSmallに固定されますが、framework moduleと生成projectのWorkers rootはReleaseSafeでも確認します。

fresh-cache確認では`ZIG_LOCAL_PKG_DIR`も空のpathへ切り替えます。global／local compile cacheの変更だけでは、取得済みのproject-local packageがlazy importの不備を隠す場合があります。CIでこの不備を検出し、`b.lazyImport`へ修正した後にNativeの初回取得とWorkersの未取得状態を検証しました。

Linuxのscaffold migration検証で、loaderに残っていたDarwin専用`dirent` layoutを検出しました。`std.c`のOS別directory APIへ置き換え、CLIも同じ標準定義を使います。複数ファイルの完全な名前、lexicographic順序、SQL内容、migration historyによる二重適用防止の回帰testを追加しました。

検証環境のmacOSのmonotonic clockは1µs分解能で、indexed SELECTが1tick未満だと正しく0nsとして計測され、既存Server-Timing testの正のduration前提が不安定になります。test queryを測定可能なrecursive SQL workloadへ変更し、失敗時のheader診断を追加しました。

## Phase 2の再評価

Phase 1の構造を踏まえ、次の設計判断が必要です。以下は実装済み機能の調査結果と設計の入口であり、Phase 2の機能変更は含めません。

1. **cf**: 最新の公式仕様を再確認し、`Operations`にprovider選択とoperation別capability表を追加します。Wranglerをdefaultに保ち、明示選択のcfが未対応なら挙動を明示します。今のargv／failure contract testを両providerへ展開できます。
2. **Form／multipart**: `http/form.zig`／`multipart.zig`とContextのparserは既にあり、field／file metadata／size limitを扱います。新parserの重複追加は避け、boundaryの厳密性とStorageへのstreamingを評価します。現在bodyはbuffer済みです。Native request読取りとWorkers bridgeの双方でstream／sink、全体／part上限、cancel／partial upload cleanupを設計してから大容量uploadを実装します。
3. **Scheduled jobs**: 既存`jobs.zig`はNativeのDB-backed queueとperiodic enqueueです。これをWorkersへ無理に移さず、Appにjob登録、platform adapterにtimer／Scheduled Event dispatchを置く最小方式を検討します。cron timezone／overlap／停止動作を決め、distributed schedulingは対象外にします。
4. **Migration**: CLIはNative／Tursoのapplication runnerとD1 SQL file経路に分かれています。共通status／up protocolとadapter選択、D1 history transaction、deploy前の明示適用を設計します。Workers scaffoldのrequest時`migrate.Once`を外す前に、初期化とmigrationの役割を分離する必要があります。
5. **Observability**: App dispatchのrequest trace、middlewareのmetrics／request ID／timing、platform clockは既存です。重複する自動設定を避けるconfig、handler errorの記録順序、Native／Workersの同じcontractを設計します。新frameworkは作りません。
