# SIMD最適化の検証結果

最終判断は、本体へのSIMD導入を見送り、実験コードと検証結果を残すことです。
長い正常入力には明確な改善がありますが、先頭DELの短い入力と、小規模HTTPの
Reactor／ReleaseSafeのP95/P99では悪化があり、暫定採用条件を満たしたとは判断できません。
HTTP／Multipartの呼び出し箇所は元のmainとバイト単位で同じ実装に戻しました。
採用済みの性能改善率はありません。以下は評価した候補の結果です。

評価した候補は、HTTPとMultipartが共有するフィールド値の制御文字検証です。
`src/internal/byte_ops.zig` で、等価なスカラー条件への整理と16バイトSIMD走査を
組み合わせています。空・1バイト入力は早期return、末尾とSIMD非対応ターゲットは
スカラー処理です。添字カウンターではなく、範囲を確認した残りのスライスを進める
実装にすることで、ReleaseSafeの不要な演算チェックも避けています。

ベースラインは `107ad5dbd1ada61cd26314e09aac837b9ce8ee2e`、最後に評価した候補コードは
`09a18f9d8fd6362715b6863964af3373615ff678` です。公開API・ABI、エラー、出力、
所有権、割り当て、既定のCPU設定は維持しています。追加依存はありません。

SIMD幅未満の改善は、等価なスカラー条件への整理によるものです。
同じ検索インターフェース同士の別実験では、1KiBのSIMD探索による時間削減は

混同していません。

初期版で確認した空・1バイトの固定コスト増加と、修正前後のraw dataも残しています。
最終版の正常な小規模入力では、5%を超える再現性のある悪化を確認していません。

暫定採用基準に対する例外もあります。ReleaseFastでは、先頭DELを即時に拒否する
単体ケースが約1.5nsから約1.8ns、16バイトブロックがある場合は約2.1nsになります。
絶対差は約0.3〜0.6nsですが、相対値では20〜40%の悪化です。ReleaseSafeでは
このケースはほぼ同等です。中央・末尾の検出は通常改善します。
「全入力で高速化した」とは報告しません。不正HTTPのネットワーク性能は正常GETの
E2Eからは判断できないため、暫定閾値に対するレビュー項目として明記します。
拒否条件やエラー契約は差分テストと既存の敵対的入力・Transportテストで検証しています。

## HTTPサーバー全体

最終候補の採否に用いたデータは `raw/final-http/` です。元のmainの実行ファイルと
最終候補を、Threaded／Reactor、ReleaseFast／ReleaseSafe、空／4KiB Cookie値の
各組み合わせで10組ずつAB/BA順に測定しました。各回サーバーを起動し直し、
1秒ウォームアップ後に5秒間、8本のkeep-alive接続で `/json` を処理します。
レスポンス本文を事前照合し、集計対象は測定中にHTTP 200のみ・エラーなしの組に限定します。

ベースラインのReactor／Fast／小規模入力で2回、この条件に反する試行がありました。
当初のハーネスが失敗したoha本文を保存していなかったため、詳細な原因は不明です。
その組の両メンバーが集計対象になる前に停止しました。失敗記録を保存するよう修正し、
未完了の組を再測定しています。完了済みの組は変更していません。詳細欠落を含む記録は
`raw/final-http/failed-attempt-reactor-fast-small-pair5.md` に残しています。

2回目はHTTP 200が369,203件、応答完了前の接続終了が2件、キャンセルが4件でした。
原因は未解決です。失敗したoha出力・stderr・サーバーログを保存し、先に完了していた
候補メンバーの4ファイルも `discarded-pair6-candidate/` に退避してから、組全体を
再実行しています。詳細は `failed-attempt-reactor-fast-small-pair6.md` にあります。
成功ペアの統計はエラーなしという条件付きの値です。信頼性の判断では、この失敗も
別途考慮する必要があります。

`raw/final-http/http-summary.csv` にrequests/sec、P50/P95/P99、対応する組ごとの
スループット改善率と95%区間、RSSスナップショット、OS報告のpeak RSS、

起動・ウォームアップ・測定・終了のサーバーCPU時間を、それらに対応する成功
リクエスト数で正規化しています。ルート直下の旧HTTPデータは初期候補の結果です。

## 不採用・保留とした候補

| 候補 | 結果と判断 |
| --- | --- |
| HTTP／Multipart共通検証 | 正常1KiBと長いCookieでは改善しますが、先頭DELのFastと小規模Reactor／Safeのテールに悪化があります。呼び出し箇所を元に戻し、私的な実験だけ残します。 |
| JSONエスケープ | 1KiBの通常ASCIIはFastで92.08%短縮。一方、密なエスケープはM2でFast 22.47%、Safe 43.69%悪化し、短いASCIIも悪化します。本体は変更しません。 |
| WebSocketマスク | byte、u32/u64、展開スカラー、vector16/32を比較。コピー後XORと融合を別計測。1KiBのvector32はコピー後XORで89.72%短縮し、融合でさらに41.43%短縮。スカラーの融合だけでは4.47%でした。小規模入力の悪化と、動的キー・割り当て込みのフレーム全体／ネットワーク計測不足のため、本体は変更しません。 |
| Form一括処理 | 1KiB通常ASCIIはスカラー一括で22.32%、ベクトル一括で92.41%短縮しますが、密な `+` は約5.4倍に遅くなります。不採用です。 |
| Form直接書き込み | ArrayListの1バイトごとの操作を除いた対照実験です。1KiBの通常ASCIIで27.61%、密な `+` で26.86%短縮しますが、URLエンコード日本語ではFast 3.12%にとどまります。アプリ全体の証拠もないため実験に残します。 |
| HTTPの名前・ターゲット・数値判定 | 有効性を示した置き換えを選んでいません。既存のセキュリティ判定を維持します。 |
| HTTP／Multipart境界探索 | std.memのSIMD探索・比較、入力長による部分文字列探索の切り替えを確認。置き換えを正当化するアプリ性能の証拠がないため維持します。 |

WebSocketの数値は固定マスク・再利用するバッファでの単体結果です。キー展開が
コンパイラに定数化される可能性があり、フレーム全体の速度として扱いません。
Formはbyte追加、スカラー直接出力、スカラー一括、SIMD一括を分けており、
ArrayList操作の削減とSIMD探索の効果を区別できます。

## サイズ・割り当て・制約

Native competitive実行ファイルはFastで1,879,184 → 1,879,296バイト（+112）、
Safeで2,287,680 → 2,287,776バイト（+96）です。本体プリミティブは割り当てません。
割り当てプロファイルの論理要求はparseが1回／896バイト、JSON header/bodyが
2回／291バイト、ウォーム後1,000 JSON応答のbacking heap割り当ては0回です。
実プロセスのメモリ・CPUは最終HTTP CSVで区別して記録します。
これらは評価した候補のサイズ・メモリです。最終判断で呼び出し箇所を元に戻したため、
ランタイム最適化とそれに伴うサイズ増加は採用していません。私的な実験モジュールは
公開ライブラリからimportされません。ベンチマーク専用の計測改善は残しています。

アプリWasmはFastで1,172,489 → 1,172,873バイト（+384）、Safeで
1,084,507 → 1,084,895バイト（+388）です。独立プローブはSIMD128なし／ありで
Fast 3,418／3,163バイト、Safe 7,735／7,476バイトでした。
アプリWasmと独立プローブのサイズは別に保存しています。プローブの縮小をアプリの
縮小として報告しません。初回ビルドと後のキャッシュ済みビルドは条件が違うため、
記録した時間・RSSからビルド時間の改善率を算出しません。cycles/opは未取得です。
他の処理と競合した初期competitive-microは参考値とし、採用の改善率には使いません。

portable-benchはReleaseSafe指定を正しく反映し、結果のチェックサムも出力するように
しました。元のmainの比較用worktreeにも同じ計測部分だけを適用しています。
差分と各モード10回の交互実行結果を `raw/portable/` 等に保存しています。
`raw/portable/summary.csv` のtyped-event encoding中央値はFast 101.5 → 101.5ns、
Safe 134 → 135nsでした。変更対象を通らない対照実験であり、SIMD改善とは数えません。
